## Services

| Service | Default port | Required env vars |
|---|---|---|
| account-service | 4001 | `PORT`, `DATABASE_URL`, `JWT_SECRET` |
| transaction-service | 4002 | `PORT`, `MONGO_URI`, `JWT_SECRET`, `ACCOUNT_SERVICE_URL` |

Both services: `require("dotenv").config()` runs first, then a `validateEnv()` check throws + `process.exit(1)` if any required var is missing. On successful start, one winston `info` line logs the port and `NODE_ENV`. Both expose `GET /health` → `{ status: "ok", service: "<name>" }`.

Run dev server: `npm run dev` (nodemon) inside each service folder. Both `index.js` files are thin now — they `require("./app")` (the real Express app, no `listen`) and only add env validation / `listen` / (transaction-service) `connectDB`. `npm test` (jest) works in both services now.

### account-service API
- `POST /users` — body `{ email }` (must contain `@`). `201 { userId, walletId, balance, currency }` (balance is a string, e.g. `"0.00"` — Postgres `numeric` via `pg`, not converted to `Number`). `400 { error: "invalid email" }` if malformed. `409 { error: "email already in use" }` on duplicate email. Creates the user + a zero-balance `INR` wallet atomically (single DB transaction in `accountRepo.createUser`).
- `GET /wallets/:userId` — **requires auth** (`Authorization: Bearer <jwt>`, 401 `{error:"missing token"}` / `{error:"invalid or expired token"}` on failure; `req.user` set to the decoded payload). `200 { userId, walletId, balance, currency }`, or `404 { error: "user not found" }`.
- `GET /internal/wallets/:userId` — same response shape as above, **no auth**. Added specifically for transaction-service's `accountClient.getWallet()` (service-to-service lookups) — the authenticated route stays as the one for real end-user access. Both share the same handler logic (`sendWalletLookup` helper in `wallets.js`).
- `POST /auth/token` (dev-only, disabled when `NODE_ENV === "production"`) — body `{ userId }` → `{ token }` signed with `JWT_SECRET`, 1h expiry. Exists purely to test protected routes locally; not a real login flow (no password/credential check).
- `POST /internal/wallets/:walletId/adjust` — body `{ amount: number > 0, type: "debit"|"credit" }` + required `Idempotency-Key` header. `400` if the header or a valid body field is missing. `200 { walletId, balance, currency }` on success. `422 { error: "insufficient funds" }` if a debit would take the balance below zero (nothing written). `404 { error: "wallet not found" }` for an unknown walletId. Replaying the same `Idempotency-Key` returns the original cached response (status + body) without re-applying the adjustment — implemented in `accountRepo.adjustBalance` via one DB transaction: check `idempotency_keys` first, then `SELECT ... FOR UPDATE` on the wallet row (see in-code comment on why the lock is needed to prevent a lost-update race between concurrent adjustments), compute/check/update, then insert the idempotency row, all before `COMMIT`.
  - Known gap (not addressed): two *simultaneous* requests with the same brand-new `Idempotency-Key` aren't fully guarded — both could pass the initial "not found" check before either commits. The second would fail at INSERT (`idempotency_keys` unique violation) and get a 500 rather than the cached response. Worth a follow-up if concurrent retries with the same key are expected.

### transaction-service data layer
- `Transaction` model (Mongoose): `fromWalletId`, `toWalletId` (String, required), `amount` (Number, required, min 0.01), `status` (enum pending/completed/failed, default pending), `idempotencyKey` (String, required, unique), `metadata` (Mixed, default `{}`), `completedAt` (Date), plus `{ timestamps: true }` → real `createdAt`/`updatedAt` (added later, see decisions log — docs created before that change have no `createdAt` and sort last under `{createdAt:-1}`).
- `transactionRepo`: `createPending({fromWalletId, toWalletId, amount, idempotencyKey})`, `markCompleted(id)`, `markFailed(id, reason)` (reason stored at `metadata.reason`), `findByUser(walletId, {limit=20, offset=0})` (matches `fromWalletId` OR `toWalletId`, sorted `{createdAt:-1}`). `createPending` does **not** catch duplicate-key errors itself — a repeated `idempotencyKey` throws a raw Mongo `E11000` (code `11000`) for whatever caller needs to handle it (currently nothing catches it explicitly — `POST /transfer` always generates a fresh `uuidv4()` per request so it never collides in practice).
- `accountClient.js`: uses a dedicated `axios.create()` instance (not the bare `axios` export) with `axios-retry` configured — `retries: 3`, `retryDelay: axiosRetry.exponentialDelay`, custom `retryCondition`: never retries a `422` (real business failure — insufficient funds), otherwise retries network errors or `5xx`. Applies to both `getWallet` (GET, naturally safe to retry) and `adjustWallet` (POST — safe to retry specifically *because* it always carries the caller's `Idempotency-Key`, so a retry either re-runs the same op or hits account-service's idempotency cache, never double-applies). `require("axios-retry").default` is the correct CJS import for the installed v4.5.0 (verified — the package is primarily ESM with a `.default` CJS interop). `getWallet(userId)` (GET `/internal/wallets/:userId`, `404` → `null`, anything else rethrows) and `adjustWallet(walletId, amount, type, idempotencyKey)` (POST `/internal/wallets/:walletId/adjust` with `Idempotency-Key` header, throws on any non-2xx).
- `GET /transactions/:userId` (`src/routes/transactions.js`) — `?limit` (default 20) / `?offset` (default 0), must be non-negative integers or `400`. `getWallet(userId)` → `404 { error: "user not found" }` if missing, else `200` with `findByUser(wallet.walletId, {limit, offset})`, newest first.
- `POST /transfer` — body `{ fromUserId, toUserId, amount }`. Validates `amount >= 0.01` (matches the schema's own `min`, not just `> 0`) and `fromUserId !== toUserId`, both non-empty strings → `400` otherwise. Looks up both wallets (`404 { error: "user not found" }` if either is missing) → creates a `pending` Transaction → debits the source then credits the destination, **using two sub-keys derived from one generated idempotencyKey** (`${key}:debit` / `${key}:credit` — see the fix noted below) → on success `markCompleted` + `201` with the transaction; on any failure from the debit/credit pair, `markFailed(id, message)` (message prefers account-service's `{error}` body, falls back to `err.message`) + `502` with the (failed) transaction. Unexpected errors elsewhere in the handler → `500`.
  - **Known, intentional gap:** if the debit succeeds but the credit fails, there's no compensating reversal — the transaction is marked `failed` and the caller gets `502`, but the source wallet stays debited. No saga/outbox pattern exists yet; worth a follow-up if this needs to be production-safe.
- **Bug found + fixed before implementing:** the task as originally described called for reusing one `idempotencyKey` for both the debit and credit calls. account-service's `idempotency_keys` table is keyed globally (not per-wallet), so the credit call would have found the debit's already-cached response and replayed it — silently never crediting the destination wallet, even though the transfer would report `201` success. Confirmed by design review before writing any code (user agreed); fixed by deriving `${idempotencyKey}:debit` / `${idempotencyKey}:credit`. Verified via curl: a real transfer moved money out of the source wallet **and** into the destination wallet correctly (125.00/75.00 after a 75 transfer on a 200/0 starting split) — this is exactly the check that would have caught the bug if the fix hadn't been applied.
- **Second issue found + fixed:** account-service's `GET /wallets/:userId` requires a Bearer JWT (added in an earlier task), which `accountClient.getWallet()` has no way to supply. Resolved (user's choice) by adding an unauthenticated `GET /internal/wallets/:userId` to account-service for service-to-service use, leaving the original route's auth intact for end-user access.
- **Bug found + fixed during testing:** `mongoose.connect()` resolves before background index builds (e.g. the unique `idempotencyKey` index) finish — confirmed via a real race: a duplicate-key insert immediately after connecting succeeded (should have failed) because the unique index didn't exist yet. Fixed by having `connectDB()` in `src/db.js` also `await Transaction.init()` (resolves once that model's indexes are confirmed built) before returning — so `index.js`'s `app.listen` never starts until the unique constraint is actually enforceable. If more models are added later, each will need the same `.init()` treatment (or switch to `mongoose.connection.syncIndexes()` for all registered models) — currently only `Transaction` is covered.
- **DB backend: MongoDB Atlas** (switched from the local `mongod`, see below). `MONGO_URI` in `.env` is a real `mongodb+srv://` connection string with live credentials (username `siddiquiahs1_db_user`, cluster `miniledger.nyjtzhh.mongodb.net`) — `.env` is gitignored, `.env.example` has a placeholder only. **Second bug found + fixed:** on this machine, Node's DNS resolver (c-ares) is configured to query `127.0.0.1`, which refuses raw SRV queries even though normal OS-level DNS resolution works fine (verified via `Resolve-DnsName` in PowerShell, which succeeded) — a known Windows+Node+Atlas quirk. This made `mongodb+srv://` lookups fail with `querySrv ECONNREFUSED` even with a correct connection string and correct Atlas Network Access rules. Fixed in `src/db.js` by calling `dns.setServers(["8.8.8.8", "1.1.1.1"])` before connecting, whenever `MONGO_URI` starts with `mongodb+srv://`. If this service is ever run on a different machine/network where the default resolver works fine for SRV lookups, this is harmless (just an extra explicit resolver).

## Pending / not yet done
- No Dockerfile in either service — `docker-compose.yml` will fail to build until added.
- Auth only guards `GET /wallets/:userId` — every other route, including everything under `/internal/` (both wallet lookup and adjust), is unauthenticated. That's fine while both services run on trusted localhost/same-network, but there's no real service-to-service auth (API key, mTLS, etc.) if this ever needs to be exposed more broadly.
- `POST /transfer` has no compensating-transaction logic — a debit-succeeds/credit-fails partial failure leaves the source wallet debited with no automatic reversal (see transaction-service section above).
- transaction-service now depends on MongoDB Atlas being reachable (internet + Atlas Network Access allowing this machine's IP) — no longer tied to the local `mongod` staying up, but also no longer works fully offline.
- No AWS or other cloud infra set up yet.
- No CI. Automated test coverage now includes: account-service's `accountRepo.adjustBalance` (mocked `pg`), `POST /users` (success + 409), `GET /wallets/:userId` (200/404/401) against a real test Postgres DB; transaction-service's `POST /transfer` (completed + failed paths) with `accountClient` mocked but real Mongo.
